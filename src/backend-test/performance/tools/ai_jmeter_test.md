# 基于 AI Skills 的全链路性能测试提效实战指南

> 本文以「传祺 2026 五一重保·车联 APP 性能测试」为真实案例，讲解如何用 7 个 AI Skills 把一次全链路性能测试从"铺人力"变成"走流水线"——每个 Skill 干什么、产出什么、和真实测试计划怎么对上。

## 一、先看清：性能测试的 8% 与 92%

一次性能测试如果只有"执行"一个动作，那它的时长只占整个周期的一小部分：

| 环节 | 占比 | 内容 | AI 能帮什么 |
|---|---|---|---|
| 需求澄清 | 高 | 接口清单、SLA 指标、生产 QPS、待确认项 | P01 一键生成澄清大纲 + P0/P1 问题清单 |
| 测试计划 | 高 | 场景组合、并发量、压测机数量、时间排期 | P02 自动算三笔账 |
| 数据构造 | 中 | 造数据量、冷热缓存、挡板 | P03 给计算公式 + 生成脚本 |
| 就绪检查 | 中 | 环境、监控、账号、依赖、脚本自检 | P04 34 项清单打钩 |
| 脚本生成 | 中 | JMX 线程组、断言、参数化、监听器 | P05 出可运行 JMX 模板 |
| **执行** | **8%** | 起压、观察、截图、记录 | 仍需人操控 |
| 报告分析 | 高 | 瓶颈定位、指标解读 | P06 四象限自动分析 |
| 报告生成 | 高 | 10 大模块、Pass/Fail 结论 | P07 一次成稿 |

> 一句话：**真正花在"按 F5 起压"上的时间只有 8%**，剩下 92% 全耗在准备、沟通、写文档上。AI Skills 的目标不是替代你执行，而是把 92% 的杂活压到 10%。

## 二、7 个 AI Skills 全景：从需求到报告一条链

```
P01 需求澄清 ──> P02 测试计划 ──> P03 数据构造 ──> P04 就绪检查 ──> P05 脚本生成---->
                                   |
                                   |
                                   |
P07 报告生成 <── P06 报告分析 <──（人工执行压测）<─────────────────┘
```

| Skill | 名称 | 输入 | 输出 | 人工介入点 |
|---|---|---|---|---|
| P01 | 需求澄清 | 接口文档 / 生产指标 / 变更说明 | 澄清大纲 10 章、待确认项 P0/P1、SLA 推荐值 | 确认 SLA 与范围 |
| P02 | 测试计划 | P01 结论 | plan_id、场景组合、压测机数、数据量、工时 | 评审排期 |
| P03 | 数据构造 | P02 数据量 | 数据计算公式、造数脚本、挡板清单 | 数据预置 |
| P04 | 就绪检查 | 全部前置产出 | 34 项就绪检查表、风险清单 | 逐项签字 |
| P05 | 脚本生成 | P01~P04 结论 | JMX 脚本（线程组/断言/参数化/监听器） | 调参、联调 |
| P06 | 报告分析 | 压测原始数据 | 四象限瓶颈图、指标对比、结论 | 复核定位 |
| P07 | 报告生成 | P06 结论 | 10 大模块正式报告、Pass/Fail | 对外发布 |

> 前 5 个 Skill 全部发生在**起压之前**，后 2 个在**压完之后**，执行阶段仍由人操控 JMeter/Locust。AI 负责"想清楚、备齐料、写得出、讲得明"，人负责"按得下、看得准、做决策"。

## 三、实战案例背景：传祺 2026 五一重保·车联 APP

### 3.1 背景与目标

- **场景**：五一假期车辆出行高峰，车联 APP 关键链路必须扛住峰值
- **对象**：18 个核心接口（车辆位置、车况、OTA、车控、车辆信息等）
- **核心指标**：目标 QPS = **生产峰值的 3 倍**（26 年春节峰值 2634 → 目标约 7200+）
- **SLA 基线**：见 4.3 节

### 3.2 项目时间轴（真实排期）

| 时间 | 里程碑 | 动作 |
|---|---|---|
| 4.21 | 方案梳理 | 梳理性能接口、生产指标、目标 TPS 评估 |
| 4.23 | 方案评审 | 产品 / 开发 / 测试 / 运维联合评审 |
| 4.24 | 第一次实施 | 环境与数据准备、脚本编写调试、执行压测、监控 |
| 4.25 | 分析调优 | 针对不达标接口分析优化 |
| 4.26 | 第二次压测 + 报告 | 复测、产出正式报告 |

> 这和 P01~P07 的链路完全对齐：**梳理 = P01/P02，实施 = P03/P04/P05+执行，调优 = P06，报告 = P07**。

## 四、P01 需求澄清：一次问清，少走 10 个来回

### 4.1 Skill 产出：需求澄清大纲 10 章

AI 根据接口文档与生产指标，一次性生成 10 个章节的澄清框架：

1. 压测范围与目标（哪些接口、达标线是什么）
2. 生产现状指标（当前 QPS、RT、P95、错误率）
3. 目标指标（3 倍 QPS、RT 上限、错误率上限）
4. 业务场景与流量模型（调用比重、峰值时段）
5. 数据要求（账号数、车辆数、参数组合）
6. 依赖与挡板（第三方系统能否隔离）
7. 环境要求（生产 / 预发布、数据库、带宽）
8. 监控与日志（全链路 traceId、应用/DB 监控）
9. 风险与回退（压测对生产的影响、限流开关）
10. 验收口径（Pass/Fail 判定规则）

### 4.2 待确认项分级：P0 阻塞 / P1 影响

AI 会顺手把所有"没写清楚的事"分成两级：

| 级别 | 含义 | 案例中的真实问题 |
|---|---|---|
| P0 | 不确认就无法开压 | 生产环境是否允许压测？sdkInit 账号频繁调用会被锁定，**剔除不压** |
| P1 | 不确认会影响结论 | 第三方（TSP / 高德 / 星河 / 实名平台 / 展厅 / 蓝牙 / 大数据 / CDP / 艾拉比 OTA）是否可 mock |
| P1 | 数据口径 | 并发数、QPS、TPS 三者口径；压测时长按多久算 |

> 案例里 `sdkInit` 接口正是靠这步澄清被排除——避免了一个"压测必失败"的坑。

### 4.3 案例 SLA 基线（可直接抄）

| 指标 | 目标值 |
|---|---|
| 单接口响应时间 RT | ≤ 200 ms |
| 错误率 | < 0.01% |
| APP → TSP 带宽占用 | < 70% |
| 应用服务器 CPU / 内存 / IO | < 80% |
| 数据库 CPU | < 2%（MySQL） |
| 慢查询 | 0 条 |
| 数据库 IO | < 5% |
| Nginx | 无 4xx / 5xx 错误 |

## 五、P02 测试计划：并发、压测机、数据量三笔账

### 5.1 场景组合：单接口 + 混合 + 生产对比

真实计划做了**三个维度**的覆盖：

| 场景 | 环境 | 目的 | 案例结果 |
|---|---|---|---|
| 单接口压测（第一轮） | 生产 | 逐个摸清每个接口的容量上限 | 18/18 通过 |
| 混合压测（第一轮） | 生产 | 贴近真实流量比例的混合压 | 目标 2300，实际 7200 |
| 单接口（副本） | 预发布 | 第三方全挡板，验证 TSP 链路 | 22 接口，需挡板 |

### 5.2 流量模型：接口比重与并发

生产真实调用占比（来自生产监控，比重 0.6 / 0.3 / 0.1 三档）：

| 接口 | 生产调用次数 | 平均 RT(ms) | P95(ms) | 最大并发 | 比重 |
|---|---|---|---|---|---|
| /vehicle/v2/findCarLocation | 5441 万 | 101 | 229 | 76 | 0.6 |
| /vehicleCondition/getVehicleStatus | 5115 万 | 69 | 95 | 52 | 0.6 |
| /standbyVehicle/.../lastExecute | 3624 万 | 103 | 234 | 45 | 0.6 |
| /vehicle/ota/upgrade/info | 1714 万 | 194 | 245 | 83 | 0.6 |
| /vehicle/carWarnInfo | 670 万 | 60 | 93 | 12 | 0.3 |
| /agreement/selectReadAgreement | 507 万 | 51 | 74 | 7 | 0.1 |
| /vehicleControl/v3/pollAccessResponse | 242 万 | 3024 | 9074 | 15 | 0.1 |

> **车控轮询接口 RT 高达 3 秒、P95 9 秒**——这类"慢而低频"的接口不能被平均 RT 掩盖，混合压测时必须单独看 P95。

### 5.3 AI 自动算的三笔账

```
压测并发数 = 生产峰值并发 × 3（目标倍数）
压测机数量 = 总目标 QPS ÷ 单机可承受 QPS（压测机 600 并发时 CPU 已达 95%）
数据量 = 每日调用量 × 覆盖天数 × 参数组合数（防"缓存命中 100%"假象）
```

## 六、P03 数据构造：让压测数据"像生产一样"

### 6.1 两个数据陷阱（AI 会在脚本里主动规避）

| 陷阱 | 现象 | 后果 |
|---|---|---|
| 数据未预热 | 冷缓存 RT 是热缓存 3~5 倍 | 首轮指标全红，误判为缺陷 |
| 数据耗尽 | 缓存命中 100%、DB 无压力 | TPS 虚高 3 倍，结论失真 |

### 6.2 案例里的数据手段

- **生产环境压测**：直接复用生产账号体系 + 真实车辆数据，减少造数成本，但要控制并发避免污染
- **预发布环境压测**：第三方全部挡板化（TSP / 高德 / 星河 / 实名 / 展厅 / 蓝牙 / 艾拉比），Mock 数据按接口维度准备
- **参数化**：vehicleId、userId、token 使用 CSV/函数变量，避免单用户数据复用触发缓存

## 七、P04 就绪检查：34 项清单拦截 90% 的返工

### 7.1 检查项分类（案例执行实录）

| 分类 | 典型项 | 案例落实 |
|---|---|---|
| 环境 | 目标环境可访问、DB 连接池充足 | 生产/预发布双环境 |
| 监控 | 运维已开应用/DB/Nginx 监控、可截图 | "运维开监控"是压测第一步 |
| 数据 | 造数完成、预热完成、挡板就绪 | 预发布 22 接口挡板全齐 |
| 脚本 | 参数化成功、断言正确、并发数核对 | 单接口/混合两套脚本 |
| 账号权限 | 压测账号可用、限流白名单 | 避开 sdkInit 账号锁定 |
| 风险预案 | 回退开关、应急联系人 | 每步观察异常即暂停排查 |

> 就绪检查的意义：**把"压到一半发现环境没配好"的概率降到 0**。案例中每次压测前都先"运维开监控 → 启动脚本 → 观察"，顺序固定、可复盘。

## 八、P05 脚本生成：把需求翻译成可执行脚本

### 8.1 JMX 脚本应包含的标准件

| 组件 | 作用 | 案例参数示例 |
|---|---|---|
| 线程组 | 定义并发与时长 | 34 / 40 / 20…（按接口热度分配线程） |
| HTTP 请求 | 接口 URL、方法、Body | POST `/vehicle/v2/findCarLocation` |
| 断言 | 校验响应码 / 业务码 | 200 + 业务 code 正确 |
| 参数化 | CSV/函数变量 | vehicleId、userId、token |
| 监听器 | 聚合报告、TPS 曲线、RT 分布 | 结果树 / 聚合报告 / 后端监听器 |
| 定时器 | 稳定吞吐（Constant Throughput Timer） | 按目标 QPS 限速 |

|---|---|---|---|
| 获取车辆位置 | 34 | 车控挑战码 V2 | 6 |
| 获取车况数据 | 40 | 获取选装包订单列表 | 24 |
| 获取备车档案 lastExecute | 20 | 获取默认车辆信息 | 14 |
| 获取 OTA 升级信息 | 20 | 初始化 sdkInit | 10 |

| 全局通知小红点 | 8 | 查询皮肤配置 | 6 |

### 8.3 压测机自身也是瓶颈

> 案例提示：**单台压测机 600 并发时 CPU 已到 95%**。分布式压测前先测压测机自身容量，否则瓶颈在压测机而非被测系统。

## 九、压测执行：人机协作的 8 分钟节奏

> AI 生成的脚本只是"弹药"，执行仍需要人按节奏开火。以下是案例实录（Locust/JMeter 通用）：

### 9.1 标准执行流程（每轮）

```
1. 运维开监控（应用/DB/Nginx/带宽）
2. 启动压测脚本
3. 前 5 分钟逐步加压：并发 1/5 → 2/5 → … → 5/5（QPS 逐级爬升）
4. 第 6~8 分钟：满负荷持续压
5. 停止压测 → 截图（QPS/TPS/RT/资源曲线）→ 下载报告
6. 关闭脚本，记录结论到压测记录表
7. 有异常接口则暂停，分析调优后进入下一轮
```

### 9.2 每一步都在观察什么

| 阶段 | 观察点 | 异常处置 |
|---|---|---|
| 1/5 ~ 3/5 | RT 是否随并发线性增长 | 曲线陡增 → 暂停排查 |
| 4/5 ~ 5/5 | CPU / 内存 / IO / 带宽是否触顶 | 单项 > 80% → 定位并调优 |
| 满负荷段 | 错误率、慢查询、P95 | 错误率 > 0.01% → 立即排查 |
| 收尾 | 恢复是否干净（无残留压测流量） | 确认后再开下一轮 |

> 压测的本质是"给系统画一条容量曲线"，逐步加压而不是一步到位，才能在曲线拐点处精准找到瓶颈。

## 十、P06 报告分析：四象限定位瓶颈

### 10.1 四象限分析法

把每个接口的压测数据丢进四象限，瓶颈一眼可见：

| 象限 | 特征 | 定位 |
|---|---|---|
| RT 高 × CPU 高 | 应用计算密集 | 代码 / GC / 线程池问题 |
| RT 高 × CPU 低 | 等待型耗时 | DB / 慢 SQL / 外部依赖（TSP） |
| RT 低 × CPU 高 | 吞吐瓶颈 | 限流 / 连接池 / 锁竞争 |
| RT 高 × 错误率高 | 不稳定 | 超时重试风暴 / 依赖抖动 |

### 10.2 案例指标解读（第一轮单接口·生产）

| 接口 | 目标并发 | 生产 QPS | 目标 QPS(3×) | 实际峰值 QPS | 平均 RT(ms) | 错误数 | 结论 |
|---|---|---|---|---|---|---|---|
| 获取车辆位置 | 180 | 154 | 462 | 584 | 278 | 100 | 通过 |
| 获取车况数据 | 300 | 258 | 774 | 777 | 292 | 131 | 通过 |
| 获取备车档案 lastExecute | 180 | 154 | 462 | 505 | 679 | 300 | 通过 |
| 获取 OTA 升级信息 | 75 | 50 | 150 | 151 | 1557 | 200 | 通过 |
| 车辆信息 | 60 | 54 | 162 | 233 | 871 | 200 | 通过 |
| 全局通知小红点 | 40 | 28 | 84 | 627 | 142 | 123 | 通过 |
| 查询皮肤配置 | 5 | 16 | 48 | 394 | 313 | 199 | 通过 |
| 蓝牙登录凭证 | 10 | 8 | 24 | 100 | 1034 | 184 | 通过 |

> 关键观察：
>
> - 所有接口**实际峰值 QPS 均 ≥ 目标 3 倍 QPS**，达标判定为"压测通过"
> - RT 普遍超 200ms 基线，但仍判通过——**说明该项目的验收核心是"吞吐达标 + 无雪崩"**，RT 作为观察项而非否决项
> - 错误数非 0 但占比极低（< 0.4%），结合错误率 0.01% 阈值判定通过

### 10.3 混合压测：验证"整体容量"

| 目标总 QPS（峰值 3 倍） | 2300 |

## 十二、案例复盘：18 个接口全部通过，背后靠什么

### 12.1 关键成功因素

1. **范围前置澄清**：sdkInit 账号锁定风险提前识别，避免无效压测
2. **目标量化**：3 倍生产峰值 QPS 一口价定死，验收口径清晰
3. **三层覆盖**：单接口（容量）→ 混合（整体）→ 预发布（挡板链路），问题在哪层一目了然
4. **人机协作**：AI 负责 92% 的准备与文档，人专注 8% 的执行决策
5. **结论对外化**：18 个接口统一"目标 QPS / 日期 / 通过"表，邮件一键发布

### 12.2 经验教训（计划中的"压测经验教训总结"留白项，建议按此模板沉淀）

| 问题事项 | 解决方案 |
|---|---|
| 第三方接口不稳定导致压测失败 | 预发布环境全部挡板化，生产环境识别可降级依赖 |
| 车控轮询接口 P95 达 9s | 单独观察 P95，避免被平均 RT 掩盖 |
| 压测机 600 并发 CPU 95% | 分布式压测前先测压测机容量 |
| 冷数据导致首轮全红 | 压测前强制数据预热 + 检查缓存命中率 |
| 账号频繁调用被锁定 | 剔除 / 使用白名单 / 多账号轮换 |
